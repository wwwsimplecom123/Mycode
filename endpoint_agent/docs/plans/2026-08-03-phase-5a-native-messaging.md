# Phase 5A Native Messaging Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use `$domain-modeling`, `$codebase-design`, `$frontend-design`, `$executing-plans`, `$tdd`, and `$verification-before-completion` in that order. Steps use checkbox (`- [ ]`) syntax for tracking. The user forbids commits, pushes, branches, and PRs.

**Goal:** Deliver the strict, offline Native Messaging protocol, testable local host, and standalone chinaccs MV3 extension foundation for Endpoint Agent Phase 5A.

**Architecture:** Native Messaging framing, untrusted JSON-to-domain conversion, and host orchestration are separate modules. The browser supplies only bounded observable mail facts; a host-owned handler validates the browser origin, builds `MailObservation`, creates local identity/time context, invokes `LocalDetectionService`, and returns its exact four-field minimal plugin projection. The extension uses only `chrome.runtime.sendNativeMessage`, a chinaccs-specific DOM adapter, and a compact warning-only status bar.

**Tech Stack:** Python 3.12 standard library, immutable dataclasses, `unittest`, Chrome/Edge Manifest V3 JavaScript, Web Crypto SHA-256, CSS, and the existing zero-dependency PEP 517 Wheel builder.

## Domain boundary decisions

- **Browser Mail Intake Adapter** is the extension's role. It observes the currently selected message and never produces an assessment or verdict.
- **Source Message Identity** is the extension-generated SHA-256 digest used to recognize the selected source message. It is not a Local Event ID and grants no ownership or permission.
- **Local Event ID** is generated by the Host for one detection and is returned only through the minimal plugin projection.
- **Browser Origin** is launch provenance supplied by Chromium to the Native Host process. It is not a mail fact, never appears in request JSON, and is checked before detection.
- **Rules-only operation** describes the useful detection capability when no formal Local Mail Risk Model runs. With the current default `UnavailableModelAdapter`, the domain execution state remains `model_unavailable`; the UI pairs the plain-language labels “纯规则模式” and “模型未安装” without inventing a second result state.
- **Unrecognized Mail Body** means no chinaccs-specific body root exists. No `MailObservation` is created and no request is sent.
- **Protection Mode status bar** communicates graded warning/status only. Closing it changes presentation, not the email or detection result.

Boundary scenarios: a JSON request that claims a high risk level is rejected before `MailObservation`; two identical source digests still receive distinct Host-generated Local Event IDs; a query-bearing page identity may be hashed locally but its raw query is never submitted; a missing Host yields a presentation state and never falls back to HTTP; a model-unavailable outcome remains a complete deterministic rule result.

## Protocol schema and resource limits

Protocol version is exactly `"1.0"`. Every request is one four-byte unsigned little-endian payload length followed by strict UTF-8 JSON. JSON roots must be objects and duplicate keys are rejected.

`ping` request whitelist:

```json
{"protocol_version":"1.0","message_type":"ping"}
```

Successful `ping` response:

```json
{"protocol_version":"1.0","message_type":"pong"}
```

`detect_mail` request whitelist:

```json
{
  "protocol_version":"1.0",
  "message_type":"detect_mail",
  "mail": {
    "source_message_id":"64-lowercase-hex-sha256",
    "subject":"string",
    "sender":"string",
    "reply_to":"string-or-null",
    "recipient_summary":["string"],
    "sanitized_body_text":"string",
    "normalized_links":["string"],
    "attachment_metadata":[
      {"name":"string","declared_type":"string-or-null","displayed_size":"string-or-null"}
    ],
    "language_hint":"zh|en|mixed|other|null"
  }
}
```

No request field carries origin, observation time, event ID, rule/model output, score/action/execution state, role/permission, Token, server address, or API key. The handler derives `source_kind="browser_native"`, `observed_at`, `local_event_id`, and the extension origin from host-controlled context.

Successful `detect_mail` response contains exactly:

```json
{
  "local_event_id":"host-generated-id",
  "risk_level":"low|medium|high|critical",
  "execution_state":"stable-domain-value",
  "generic_action":"continue|verify_sender|avoid_credentials|contact_security"
}
```

Every failure response contains exactly `{"error_code":"stable_lower_snake_code"}`.

`NativeLimits` is centralized in `native_protocol.py` with: 262,144 frame bytes; 128 source-ID characters; 512 subject/address characters; 32 recipients of at most 256 characters; 16,384 body characters; 256 links of at most 2,048 characters; 128 attachments; attachment name 512, declared type 255, and displayed size 64 characters; language hint 16 characters. Limits reject rather than truncate.

## Origin allowlist and plugin permissions

- Development Native Host name: `cn.shielddome.endpoint_agent`.
- Development extension origin: one fixed `chrome-extension://<32-character-development-id>/` constant shared by Python tests, extension documentation, and `native_host/com.shielddome.endpoint_agent.development.json`.
- The manifest uses one literal `allowed_origins` entry. Wildcards and HTTP(S) origins are forbidden.
- The host receives browser origin from the Chromium launch argument; request JSON has no origin field and cannot override it.
- The extension manifest grants only `nativeMessaging`, declares background service worker, loads `adapters/chinaccs.js` before `content.js`, applies `style.css`, and matches exactly `https://webmail.chinaccs.cn/*`.
- No optional host permissions, storage permission, remote code, CDN, or network client API is present.
- The fixed ID and manifest path are explicitly development-only; Phase 5B replaces them with enterprise deployment values and browser registration.

## Status-bar design system

Subject: an employee reading one enterprise webmail message. The bar's single job is to state local detection availability/result without competing with the email.

- Palette: `ink #172033`, `surface #F6F8FB`, `border #C8D0DC`, `safe #16734A`, `caution #9A5B00`, `danger #B42318`. Color is always paired with an icon and text state.
- Type: inherit `Segoe UI`, `Microsoft YaHei`, and system sans for status/copy; use `Consolas`, `SFMono-Regular`, monospace only for the Local Event ID. No remote fonts.
- Layout: 34–42 px compact inline bar inserted immediately before the recognized mail body, wrapping into a second line only on narrow widths.

```text
┌─ status rail ─┬─ icon  ShieldDome · 风险：高  · 纯规则模式 / 模型未安装 ─┬─ × ─┐
│               │  建议：不要输入账号密码        事件 ID: event-…             │     │
└───────────────┴──────────────────────────────────────────────────────────────┴─────┘
```

- Signature: a narrow left “status rail” with a simple shield glyph creates a recognizable safety-instrument cue while the rest stays quiet and rectangular.
- Motion: only the detecting glyph rotates; `prefers-reduced-motion: reduce` disables it. No entrance animation.
- Semantics: progress uses `role="status"`; risk/error uses `role="alert"`; close is a keyboard-focusable button with visible focus. The bar never uses fixed positioning, never overlays the message, and contains no destructive control.
- Self-critique: the shield rail is the one distinctive device. Gradients, shadows, large radius, promotional copy, and extra badges are removed because they would make an embedded mailbox instrument read like a generic product card.
